# Stage 8 — Follow the person across the region (journey view + corridor map) and a congestion-based fatigue model (brief for Muse)

Agent mode, rules in `AGENTS.md`. Builds on stage 7 (Now card, cause objects, highlighting, `scenarios/criteria/kr-default.json`) — read `briefs/07-RESULT.md` first. Sub-agents allowed (Muse only; Part A pipeline and Part B data are independent). Sandbox: no network, no keys.

User feedback (verbatim intent): "The map should load wherever the simulated person goes — or when they leave for another area, show the movement at a larger scale. And show that person's **fatigue** based on how congested the route is. Right now there's no such information; things just move, so nothing is legible."

The demo household: home A 잠실 레이크팰리스, home B 판교 백현마을, work near 판교역. From A the commute leaves the built 잠실 area by subway and arrives in the built 판교 area — today that leg is invisible (only a ride-minutes number).

## Part A — journey view and corridor map
1. **Station network from OSM** (`data/raw/south-korea-latest.osm.pbf`, pipeline in Python like stage 1): subway/rail route relations for the 수도권 lines — at least 2호선, 8호선, 9호선, 분당선(수인분당선), 신분당선 — with stop order, station nodes (name, line, coordinates) and line geometry. Build a station graph (transfers between same-name stations). Path for a station ride = shortest by line distance with a transfer penalty (criterion). Output `data/build/region/network.json` (+ simplified geometry). Never commit build output.
2. **Ride time.** Keep the customer's `ride_minutes` (가정값/고객 입력) as the total; split across legs in proportion to line distance, plus a transfer walk/wait per transfer (criterion, 가정값). Show the split in the UI ("2호선 잠실→강남 약 14분 · 환승 4분 · 신분당선 강남→판교 약 17분 — 합계는 고객 입력 35분").
3. **Corridor map.** For each station-ride path in the scenario, generate a low-detail corridor: buildings within ±250 m of the line between the two built areas from `data/raw/buildings` (GIS footprints, height estimate as stage 1, flat colour, no textures, merged per tile), major roads (OSM motorway/trunk/primary), the Han river / water, district boundaries, station markers with names. Tile it (e.g. 1 km tiles) and lazy-load tiles in the browser as the journey camera approaches; dispose tiles far behind. Budget: corridor for 잠실→판교 must load in < 2 s on medium and stay under the stage-6 draw-call budget (log it). Label the corridor "간략 지도 (건물 높이 추정)".
4. **Journey camera.** When the followed member starts a station ride: the camera smoothly rises from the street to a regional height (both ends + the line in frame), the line is drawn, a train marker moves along the real geometry at the split pace, current line/station label and minutes left are shown; at the destination it descends into the built area (판교 detailed scene already exists — load both areas' detailed data on the itinerary, not only the home area). If the destination is not a built area, stay at the corridor level and say "상세 지도는 지역 생성 후". The sim clock keeps running; at 60× the journey still takes a few seconds — never skip it silently. User can press "거리 보기" to stay low or "전체 경로" to stay high.
5. **Itinerary-driven loading.** When a member is followed, preload every area/corridor their day touches (home area, work area, corridors). Show a small loading line in the Now card ("판교 지도 불러오는 중…").

## Part B — congestion data and fatigue model
1. **Subway congestion (real data).** `data/raw/traffic/서울교통공사_지하철혼잡도정보_20260930.xlsx` (Seoul Metro 1–8호선, sheets 평일/토요일/일요일; columns 호선, 역번호, 역명, 상하구분, then 30-minute slots 05:30~06:00 … ; value = average congestion %, 34 % ≈ all seats taken, 100 % = rated capacity). Loader (openpyxl is installed in `.venv`) → per line/station/direction/slot. Direction (상선/하선, 내선/외선 for 2호선) must be derived from stop order. Lines not covered (신분당선, 분당선 if absent, 9호선) → **no data**: show "혼잡도 자료 없음" and use the criterion's 가정값, visibly. License: 공공누리 3유형 (출처표시+변경금지) — use values for computation and display with attribution "서울교통공사 지하철혼잡도정보 (2026-09-30 기준)"; **do not commit or redistribute the file or derived tables**.
2. **Road / street busyness.** Our residents walk and ride; there is no car leg. Do not invent road traffic. For walking legs show only what we know (graph distance, crossings count, road class walked along from OSM). Note in the result that road traffic needs the Seoul real-time traffic API key (orchestrator will ask the user) and a car mode, as later work.
3. **Fatigue model ("피로도 지수 · 가정 모델").** Transparent, deterministic, 0–100, per member per minute, every weight a criterion in `kr-default.json` with source 가정값 and editable:
   - load from walking minutes, from standing ride minutes (probability of standing rises with congestion: ≤34 % seated, then increasing), from crowding above 100 % (extra per minute), per transfer, per waiting minute;
   - recovery while at home / seated stays; overnight reset to a baseline;
   - lunch and weekend effects only via the activities the engine already simulates.
   Label everywhere: "가정 모델이며 건강·의학적 판단이 아닙니다". No single "better home" verdict.
4. **Engine output.** Each trip leg carries `congestion` ({line, station, direction, slot, value_pct, source: "서울교통공사"|"가정값"}) and `fatigue_delta`; per member a fatigue series per day; summaries: arrival-at-work fatigue, after-commute-home fatigue, 30-day average, minutes in crowding > 100 %. Deterministic; recorded runs still replay.

## Part C — make it legible (UI + agent)
1. Now card (stage 7) gains a **피로도 bar** with the current value and the delta of the current leg ("+12 · 2호선 잠실→강남 혼잡도 148 %, 서서 감"), and the cause chips (criterion ids).
2. In the journey view, colour the line by congestion per segment for the current 30-minute slot (legend: 여유 / 보통 / 혼잡 / 매우 혼잡, with %), source badge per segment (실측 / 가정값).
3. A·B 비교 and 삶의 질 cards: add 출근 도착 피로도, 퇴근 후 피로도, 30일 평균, 혼잡 100 % 초과 탑승 시간 — with units and badges. Day view: a small fatigue line over the day for the followed member with event markers.
4. Consult agent tools: `get_journey(run, day, member)` (legs, lines, split minutes, congestion per leg with source), `get_fatigue(run, member, day?)`, and the criteria tools cover the fatigue weights. The agent must say the fatigue index is a stated model, cite criterion ids and data sources, and never give health advice.
