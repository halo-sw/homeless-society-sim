## Part B — "시뮬레이션 상담" agent
A side panel (Astryx `Chat` in a `Drawer`/side layer, open by default on first visit, toggle button "상담") where the customer talks to a Muse agent that sets up, runs, explains and re-runs the simulation.
1. **Server side only** (keys never in the browser): `web/src/consult/` Node modules + Vite dev middleware `POST /api/consult` (same pattern as `/api/judge`). Provider via the existing `web/src/judge/providers.js` (meta default `muse-spark-1.3`, `reasoning_effort: "low"`, `max_tokens` 2000; baseten selectable). Facts verified by the orchestrator today: the Meta API supports OpenAI-style `tools` / `tool_calls` (`finish_reason: "tool_calls"`, `message.tool_calls[].function.arguments` JSON string); reply to a tool call with `{role: "tool", tool_call_id, content}`.
2. **Tools** (pure handlers, unit-tested, all numbers from data/engine):
   - `get_scenario()`, `update_scenario(patch)` — household members, roles, workdays, work (`station_ride` with `station_name` + `ride_minutes` **only if the customer stated the number**; store `ride_minutes_source: "user_input"`), errands, preferences, homes. Validates against the schema; returns errors to the model.
   - `list_areas()` (the built areas only), `list_complexes(area, query?)`, `find_places(area, category)` (real POIs with graph minutes from a home), `list_stations(area)`.
   - `run_simulation(home: "A"|"B"|"both", decisions: "rules"|"recorded"|"muse")` — runs the engine in-process; `muse` uses the judge layer (warn about cost/time; cap ≤ 1 per conversation), returns the compare summary and run id.
   - `compare(run_a, run_b)`, `get_day(run, day, member)` (trips with minutes/metres), `explain_decision(run, decision_id)`.
   - `set_view({home, day, time, follow, mode})` — returned to the browser so the agent can **show** what it explains (the UI applies it and shows a chip "화면 이동: B · 3일차 08:18").
3. **Behaviour.** Korean, short. On first open it greets and asks setup questions one at a time (who lives, workdays, work station, ride minutes — say the app cannot know transit times and the number will be labelled 가정값; daily habits). Then offers to run. Answers questions only from tool results; for "what if" it patches a copy of the scenario, re-runs, and reports before/after. Max 6 tool rounds per turn. If asked about another place: only the four built areas today; say nationwide generation is the next stage.
4. **Guards** (reuse/extend the judge guards): every number in the answer must appear in a tool result of this conversation (same rounding rules as 4c); refuse and redirect price forecasts, investment advice, safety/crime, school quality, health/medical; never claim the simulation predicts real life — it is a scenario with stated assumptions. On guard failure, retry once with a correction note, then answer with the tool numbers only.
5. **Transparency in the UI.** Tool calls render as compact Astryx chat tool-call rows (name + short result), with provider Badge and a per-conversation token/cost counter. Conversations live in browser memory only; the server stores nothing.
6. Production build: the panel shows "상담은 로컬 개발 서버에서 Muse 키로 동작합니다" and a recorded demo transcript (`scenarios/consult-demo.json`, written by the orchestrator later; ship an empty-state if absent).
