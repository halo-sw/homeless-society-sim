Agent mode, rules in `AGENTS.md`. Read `briefs/03-RESULT.md`, `docs/scenario-schema.md`, `web/src/engine/` first. Attached: playback captures after stage 3 (`briefs/img/03-render.png`; rows = sim A 07:30 follow / sim B 07:30 follow, sim A 19:00 / 02:00, tour 잠실 stop 2 / 판교 stop 0). Sandbox has no network and no keys: build everything against recorded fixtures; the orchestrator runs the live calls.

Why this stage matters: the hackathon requires real use of Meta models in the product, and two bonus prizes reward (a) agentic use — autonomy, effectiveness, usefulness — and (b) running on the open-weight **Muse Spark Open**. So the simulated household members must actually decide with a Meta model, the decisions must be logged and replayable, and the provider must be swappable.

## Part B — judgment layer (`web/src/judge/`, Node-side; keys never reach the browser)
1. **Providers** (OpenAI-compatible chat completions, `fetch`, no SDK):
   - `meta`: base `https://api.meta.ai/v1`, model `muse-spark-1.3`, key env `MODEL_API_KEY` (Bearer).
   - `baseten`: base `https://inference.baseten.co/v1`, model `meta-models/muse-spark-open-1026`, key env `BASETEN_API_KEY` (Bearer). Mark the base URL/auth as "to be confirmed by the orchestrator".
   - Same interface `complete({system, user, schema}) → {json, usage, latency_ms, provider, model}`; structured output via `response_format: {type: "json_schema", ...}`, with a fallback parse of a JSON-only reply if the provider rejects `json_schema`. Timeouts, retry with backoff on 429/5xx, ≤ 4 concurrent requests.
2. **What is decided.** Only the household members' records (stage 3: 81 per run in A); background neighbours stay rule-based. Kinds: the existing `shop_choice`, `park_or_home`, `station_route`, plus a new **weekend plan** per member per weekend day: choose up to 3 activities from the categories that actually exist reachable in the area (with graph minutes), in order. The engine then executes the plan with real paths.
3. **Agent context.** Each call gets: the member's profile from the scenario (role, a short free-text `preferences` the user writes — add the field, demo text in Korean, no health/medical content), the day/time, today's trips so far and the last 3 decisions with their reasons (short memory), and the options with numbers from the graph. Output schema: `{chosen_key, reason_ko (≤ 60 chars), reason_en (≤ 90 chars)}` (weekend plan: `{plan: [keys], reason_ko, reason_en}`).
4. **Guards.** The model chooses; it never changes numbers. Reject and fall back to the rule (logged as `chosen_by: "rule_fallback"`, with the reason) when: the key is not an option, a number in the reason does not appear in the options, or the reason mentions price, safety, crime, school quality, health. Never send personal data; the household is simulated.
5. **Record and replay.** `node web/scripts/judge.mjs --scenario scenarios/demo-two-homes.json --home A|B|both --provider meta|baseten [--dry-run]` runs the engine with a hook that calls the provider sequentially per member (deterministic call order), writes `scenarios/decisions/<scenario>-<home>-<provider>.json` (decisions with reasons, provider, model, tokens, latency; no keys, no raw headers) and a usage summary (calls, tokens in/out, estimated USD using: meta $1.25 / $0.15 cached / $4.25 per 1 M tokens; baseten: tokens only). Replay: `simulate.mjs --decisions <file>` → zero provider calls, byte-identical output. `--dry-run` prints the planned call count and estimated tokens without network. Target: ≤ $1 per 30-day run with `meta`.
6. **Live demo path.** In `vite dev` only: a middleware `/api/judge` (server side, key from env) so the browser can ask Muse about the current decision live; UI button "Muse에게 묻기" on a decision caption shows a spinner, then the reason and the chosen option, with a "live" badge and provider/model name. Production build never contains keys or calls; it uses committed decision files.
7. **UI.** In sim mode, when a household member reaches a branch point, show a caption: options with minutes, the chosen one, and the reason in Korean (badge: `Muse Spark 1.3` / `Muse Spark Open` / `규칙`). A small "판단 기록" panel lists today's decisions. Compare panel adds: how many decisions came from the model vs fallback.
